# Propely — Agent Instructions (.agent.md)

## 0) Priority (non-negotiable)
1. Follow this `.agent.md`.
2. Follow the current task file in `docs/tasks/`.
3. Follow `docs/roadmap.md` for execution order.
4. If anything conflicts, prefer: correctness > security > simplicity > consistency.

## 0.1) Autonomous Workflow
When the user says **"next task"**:
1. Read `docs/roadmap.md` to determine the current phase and next eligible task.
2. Select the first PENDING task whose dependencies are all met.
3. Create task file: `docs/tasks/NNNN-<title>.md`
4. Create walkthrough file: `docs/walkthroughs/NNNN-<title>.md`
5. Implement the solution following Clean Architecture layers.
6. Run quality gates (build, tests).
7. Update walkthrough with results.
8. Commit with conventional format: `feat|fix|test(scope): message (#NNNN)`
9. Mark task DONE in roadmap.

See [.agent/rules/autonomous-workflow.md](.agent/rules/autonomous-workflow.md) for full details.
See [docs/roadmap.md](docs/roadmap.md) for execution phases and dependency graph.

## 1) Language
- **English only** in repository content: code, comments, docs, commit messages, logs, scripts, configs.

## 2) Repository documentation rules
- Tasks live in: `docs/tasks/NNNN-*.md`
- Walkthroughs live in: `docs/walkthroughs/NNNN-*.md`
- Every task MUST have a walkthrough with the **same file name**.
- If any work is done, the walkthrough must be updated in the same change set/commit.

Naming conventions:
- Standard: `NNNN-...`
- Fast track: `ft-NNNN-...`
- Code review: `cr-NNNN-...`

## 3) Delivery workflow (how work is performed)
For each task:
1. Read the task file and restate the goal in your own words (briefly, in the walkthrough).
2. Implement the smallest correct solution that satisfies acceptance criteria.
3. Keep changes cohesive. Avoid "drive-by refactors".
4. Update the walkthrough with:
   - decisions, trade-offs
   - commands run
   - files changed
   - tests executed
   - follow-ups/backlog items
5. Ensure quality gates pass locally (or document why not).

## 3.1) Task integrity & scope discipline

### Task Document Preservation
The task document is the immutable specification. Only the Status field and Definition of Done checkboxes may be modified when completing a task. All original sections must be preserved. Implementation notes go in the walkthrough, not the task file.

### Scope Discipline
Only create, modify, or delete files directly required by the task scope. Note out-of-scope ideas in the walkthrough Follow-ups section instead.

### Manual Verification
If a task's Testing Plan includes manual verification steps, complete all automated work first, then explicitly ask the user to perform the manual steps before the task is marked DONE.

## 4) Architecture rules (Clean Architecture + DDD)
- Use Clean Architecture layers:
  - **Domain**: pure, no framework dependencies.
  - **Application**: use cases, CQRS, interfaces/ports, orchestration.
  - **Infrastructure**: Postgres/Redis/RabbitMQ/HTTP clients, implementations.
  - **Presentation**: API endpoints, DTOs, request validation, auth policies.
- DDD:
  - Prefer explicit domain models and invariants.
  - Avoid anemic domain when rules exist.
- CQRS:
  - Commands mutate state; Queries read state.
  - Prefer separate query models if needed.

## 5) Monorepo structure
```
apps/web/                          # Next.js 16 frontend (port 3000)
services/ai-api/                   # .NET 10 AI API — internal utility (port 5010)
services/orgs-api/                 # .NET 10 Orgs API — auth/tenancy (port 5020)
services/properties-api/           # .NET 10 Properties API — core domain (port 5030)
services/publishing-api/           # .NET 10 Publishing API + worker (port 5040)
services/contacts-api/             # .NET 10 Contacts/Leads API (port 5050)
services/appointments-api/         # .NET 10 Appointments/Calendar API (port 5060)
```

Each .NET service has its own solution file and follows:
```
src/
  Propely.<Service>.Domain/          Pure business logic, entities, events
  Propely.<Service>.Application/     Use cases, commands, queries, interfaces
  Propely.<Service>.Infrastructure/  EF Core, RabbitMQ, Redis, external services
  Propely.<Service>.Api/             Controllers, middleware, configuration
  Propely.<Service>.Client/          NuGet SDK (Refit client, DTOs, DI extension)
```

## 5.1) NuGet SDK convention
Services consumed by other services publish a `Propely.<Service>.Client` NuGet package containing:
- Refit interface (`I<Service>ApiClient`)
- DTOs (request/response models)
- DI extension (`Add<Service>Client(this IServiceCollection, Action<ClientOptions>)`)
- `TenantDelegatingHandler` for automatic `X-Tenant-Id` header propagation

| Service | Publishes Client | Consumed By |
|---------|-----------------|-------------|
| ai-api | `Propely.AiApi.Client` | properties-api, publishing-api |
| properties-api | `Propely.PropertiesApi.Client` | publishing-api |
| contacts-api | `Propely.ContactsApi.Client` | publishing-api |
| orgs-api | `Propely.OrgsApi.Client` | all services |

## 6) Event-driven baseline (RabbitMQ)
- Events are immutable facts: `SomethingHappenedV1`.
- Prefer **one event type per fact**.
- Versioning: add new fields as optional when possible. Breaking changes require `V2`.
- Always include: `EventId` (GUID), `OccurredAtUtc`, `CorrelationId`, `CausationId`, `Producer`, `SchemaVersion`
- Idempotency is mandatory for consumers.

### Outbox pattern (mandatory where applicable)
- If publishing events after DB writes, use an outbox table + background dispatcher.
- Never "write DB then publish directly" if it can cause inconsistency.

## 7) Data layer baseline (Postgres)
- Prefer migrations (no manual DB drift).
- Enforce constraints at DB level where reasonable (FKs, unique indexes).
- Always use parameterized queries / ORM safe patterns.
- Database naming: `propely_<servicename>` (e.g., `propely_propertiesapi`).

## 8) Cache layer baseline (Redis)
- Cache is an optimization, not a source of truth.
- All cached entries must have TTL.
- Include cache key conventions in code (predictable prefixes).

## 9) API security baseline (ASP.NET Core .NET 10)
Minimum requirements for any exposed API:
- HTTPS only, HSTS in production.
- Security headers (at least: X-Content-Type-Options, X-Frame-Options or CSP, Referrer-Policy).
- Input validation at the edge (request DTO validation).
- Authentication ready-by-default (JWT bearer).
- Authorization policies (no role strings scattered across endpoints).
- Rate limiting enabled (sane defaults).
- No secrets in repo. Use `.env` + `.env.example`.

## 10) Observability baseline (non-negotiable)
- OpenTelemetry for traces + metrics.
- Structured logging with correlation IDs.
- Logs must not contain secrets or PII.
- Health endpoints:
  - liveness (process)
  - readiness (dependencies: db/rabbit/redis)

## 11) Quality gates (Definition of Done)
A task is "DONE" only when:
- Acceptance criteria are met.
- Code builds.
- Tests are added/updated and pass.
- Formatting/analyzers pass (or the failure is fixed).
- Security baseline is not violated (no secrets, no unsafe defaults).
- Walkthrough is updated and accurate.

## 12) Output discipline
When asked to produce repository artifacts:
- Prefer creating/updating files, not long chat explanations.
- Keep changes minimal but correct.
- Don't invent requirements. If task is ambiguous, write assumptions in the walkthrough and proceed with the safest default.

## 13) Pull request creation

5. Fill ALL sections of the template
6. If the task metadata includes `- GitHub Issue: #NNN`, include `Closes #NNN` in the PR body
7. Report PR URL to user

See [.agent/rules/pr-workflow.md](.agent/rules/pr-workflow.md) for full details.

## 14) UI Design workflow (Google Stitch)
- All UI designs are generated via **Google Stitch (Pro model)** with detailed prompts.
- Implementation must be **pixel-perfect** against the Stitch output.
- Workflow:
  1. Generate Stitch screen design → save HTML to `.stitch-html/<screen-name>.html`
  2. Extract exact CSS, spacing, colors, typography
  3. Implement in Next.js matching pixel-for-pixel
  4. Verify visually
