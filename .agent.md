# Propely — Agent Instructions (.agent.md)

## 0) Priority (non-negotiable)
1. Follow this `.agent.md`.
2. Follow the current task file in `docs/tasks/`.
3. Follow `docs/roadmap.md` for execution order, then `docs/backlog/` for details.
4. If anything conflicts, prefer: correctness > security > simplicity > consistency.

## 0.1) Autonomous Workflow
When the user says **"next task"**:
1. Read `docs/roadmap.md` to determine the execution phase order and next eligible task.
2. Read `docs/backlog/` epic files to get current task statuses and verify dependencies are DONE.
3. Select the first PENDING task **in roadmap phase order** (0 → 1 → 2 → 3 → 4 → 5 → 6 → 7) whose dependencies are all met.
4. Create task file: `docs/tasks/NNNN-<title>.md`
5. Create walkthrough file: `docs/walkthroughs/NNNN-<title>.md`
6. Implement the solution following the **use case → design → TDD** flow (see §3.2).
7. Run quality gates (build, tests).
8. Update walkthrough with results.
9. Commit with conventional format: `feat|fix|test(scope): message (#NNNN)`
10. Mark task DONE in backlog.

See [.agent/rules/autonomous-workflow.md](.agent/rules/autonomous-workflow.md) for full details.
See [docs/roadmap.md](docs/roadmap.md) for execution phases and dependency graph.

## 0.2) Epic Workflow
When the user says **"next epic"** (or **"next epic: P<X>"**):
1. Select target epic: first epic in roadmap phase order with remaining actionable tasks (or user-specified).
2. Plan execution order (topological sort by dependencies).
3. Execute ALL actionable tasks sequentially without pausing (docs → implement → test → commit → mark complete).
4. Run final quality gate across all services.
5. Create ONE combined PR for the entire epic.

See [.agent/rules/epic-workflow.md](.agent/rules/epic-workflow.md) for full details.

## 1) Language
- **English only** in repository content: code, comments, docs, commit messages, logs, scripts, configs.

## 2) Repository documentation rules
- Tasks live in: `docs/tasks/NNNN-*.md`
- Walkthroughs live in: `docs/walkthroughs/NNNN-*.md`
- Every task MUST have a walkthrough with the **same file name**.
- If any work is done, the walkthrough must be updated in the same change set/commit.

Naming conventions:
- Standard: `NNNN-...`
- Fast track: `ft-NNNN-...`
- Code review: `cr-NNNN-...`

## 3) Delivery workflow (how work is performed)
For each task:
1. Read the task file and restate the goal in your own words (briefly, in the walkthrough).
2. Implement the smallest correct solution that satisfies acceptance criteria.
3. Keep changes cohesive. Avoid "drive-by refactors".
4. Update the walkthrough with: decisions, trade-offs, commands run, files changed, tests executed, follow-ups.
5. Ensure quality gates pass locally (or document why not).

### 3.1) Task integrity & scope discipline

#### Task Document Preservation
The task document is the immutable specification. Only the Status field and Definition of Done checkboxes may be modified when completing a task. Implementation notes go in the walkthrough, not the task file.

#### Scope Discipline
Only create, modify, or delete files directly required by the task scope. Note out-of-scope ideas in the walkthrough Follow-ups section.

#### Manual Verification
If a task's Testing Plan includes manual verification steps, complete all automated work first, then explicitly ask the user to perform the manual steps before the task is marked DONE.

### 3.2) Use Case → Design → TDD Flow (mandatory for UI tasks)

Before implementing any screen or user-facing feature:

1. **Define use cases exhaustively:**
   - Actor, preconditions, main flow, alternative flows, error flows, postconditions
   - Document in the task file or walkthrough
   - Get user validation if use cases involve ambiguous requirements

2. **Generate Stitch MCP design:**
   - Use `generate_screen_from_text` with Stitch Project ID `11823747923864658899` and `modelId: GEMINI_3_PRO`
   - Input: the use cases, the design system tokens, and any related screens
   - Download HTML to `.stitch-html/<screen-name>.html`
   - The Stitch design is the **single source of truth** for layout, spacing, colors, and typography

3. **Implement with TDD:**
   - **Red:** Write failing tests (unit + integration) that capture acceptance criteria
   - **Green:** Write minimum code to make tests pass
   - **Refactor:** Clean up while tests stay green
   - Verify pixel-perfect alignment against Stitch design

4. **Verify:** Screenshot comparison against Stitch design, full test suite green

### 3.3) TDD requirements (mandatory for all backend tasks)

Every command/query handler, domain entity, and API endpoint MUST follow TDD:
- Write tests FIRST that define expected behavior
- Tests must cover: happy path, validation errors, authorization failures, edge cases
- Coverage targets: Domain >90%, Application >80%, Infrastructure >60%, API >50%, Frontend >70%

## 4) Architecture rules (Clean Architecture + DDD)
- Use Clean Architecture layers:
  - **Domain**: pure, no framework dependencies.
  - **Application**: use cases, CQRS, interfaces/ports, orchestration.
  - **Infrastructure**: Postgres/Redis/RabbitMQ/HTTP clients, GCP Cloud Storage, implementations.
  - **Presentation**: API endpoints, DTOs, request validation, auth policies.
- Namespaces: `Propely.<Service>.<Layer>` (e.g., `Propely.PropertiesApi.Domain`)
- DDD: prefer explicit domain models and invariants. Avoid anemic domain when rules exist.
- CQRS: Commands mutate state; Queries read state. One handler per use case.

Each .NET service follows:
```

  Propely.<Service>.IntegrationTests/
```

### 5.1) NuGet SDK conventions
Inter-service communication uses Refit NuGet SDK clients:
- Each service publishes a `Propely.<Service>.Client` project
- Client contains: Refit interface, request/response DTOs, `IServiceCollection` extension
- Tenant context propagated via `TenantDelegatingHandler` (adds `X-Tenant-Id` header)
- Resilience via Polly (retry + circuit breaker)

| SDK | Published by | Consumed by |
|-----|-------------|-------------|
| `Propely.OrgsApi.Client` | orgs-api | All backend services |
| `Propely.AiApi.Client` | ai-api | properties-api |
| `Propely.PropertiesApi.Client` | properties-api | publishing-api, contacts-api, appointments-api |
| `Propely.ContactsApi.Client` | contacts-api | appointments-api |

## 6) Event-driven baseline (RabbitMQ)
- Events are immutable facts: `SomethingHappenedV1`.
- Versioning: add new fields as optional when possible. Breaking changes require `V2`.
- Always include: `EventId`, `OccurredAtUtc`, `CorrelationId`, `CausationId`, `Producer`, `SchemaVersion`
- Idempotency is mandatory for consumers.
- Outbox pattern: if publishing events after DB writes, use an outbox table + background dispatcher.

## 7) Data layer baseline (Postgres)
- Prefer migrations (no manual DB drift).
- Enforce constraints at DB level (FKs, unique indexes).
- Always use parameterized queries / ORM safe patterns.
- One database per service: `propely_aiapi`, `propely_orgsapi`, `propely_propertiesapi`, `propely_contactsapi`, `propely_appointmentsapi`, `propely_publishingapi`.

## 8) Cache layer baseline (Redis)
- Cache is an optimization, not a source of truth.
- All cached entries must have TTL.
- Cache key conventions with predictable prefixes.

## 9) API security baseline
- HTTPS only, HSTS in production.
- Security headers (X-Content-Type-Options, X-Frame-Options or CSP, Referrer-Policy).
- Input validation at the edge (FluentValidation on request DTOs).
- JWT bearer authentication (tokens issued by orgs-api).
- Authorization via permission-based policies (not hardcoded role checks). Use `IPermissionEvaluator`.
- Rate limiting with sane defaults.
- No secrets in repo. Use `.env` + `.env.example`.

## 10) Observability baseline
- OpenTelemetry for traces + metrics.
- Structured logging with correlation IDs.
- Logs must not contain secrets or PII.
- Health endpoints: liveness (process) + readiness (dependencies).

## 11) Quality gates (Definition of Done)
A task is "DONE" only when:
- Acceptance criteria are met.
- Code builds.
- Tests are added/updated and pass (TDD followed).
- Formatting/analyzers pass.
- Security baseline is not violated.
- Walkthrough is updated and accurate.

## 12) Output discipline
- Prefer creating/updating files, not long chat explanations.
- Keep changes minimal but correct.
- Don't invent requirements. If ambiguous, write assumptions in the walkthrough.
